# Ki-Buddy 产品开发规范

Ki-Buddy 是长期跟随 AionUi 演进的独立产品。本规范只约束一件事：产品能力如何接入 AionUi，同时把上游同步的冲突限制在少量、稳定、可验证的 **seam（集成接缝）** 中。

本规范不复制通用工程规则。文件结构、进程边界、测试和 i18n 分别遵循 `architecture`、`testing`、`i18n` skill；领域行为由 issue、spec 和 ADR 定义。

本规范的产品接缝规则只适用于应用 runtime 与其直接消费的配置。纯 CI/CD、打包、发布、版本映射和来源验证变更按第 2.3 节处理，不属于功能开发接缝。

## 1. 上游优先

AionUi 源码是持续更新的基线。实现 Ki-Buddy 能力时，按以下顺序选择方案：

1. 使用 AionUi 已有公开接口、配置、组件或 service。
2. 在产品拥有文件中组合上游能力。
3. 在上游拥有文件中增加一个薄接缝，将控制权交给产品模块。
4. 只有变更脱离 Ki-Buddy 后仍对 AionUi 成立时，才把它作为通用改进实现。

Ki-Buddy 产品模块可以依赖 AionUi 公开模块；AionUi 通用领域模块不依赖 Ki-Buddy 业务实现。必须由上游入口选择产品行为时，入口只通过 capability、adapter、factory、handler、Gate 或 lazy entry 装配产品模块。

完成标准：产品规则位于产品拥有文件；Ki-Buddy 自有改动在上游拥有文件中只包含薄接缝或真正的通用改进。

## 2. 所有权与变更分类

所有权描述谁决定文件的长期结构；变更分类描述本次为什么修改它。两者不能混为一类。

### 2.1 文件所有权

| 所有权   | 判定                                | 维护规则                                                      |
| -------- | ----------------------------------- | ------------------------------------------------------------- |
| 产品拥有 | 文件名、目录或配置明确属于 Ki-Buddy | 产品可以独立演进，仍遵循仓库通用工程规范                      |
| 上游拥有 | 其余 AionUi 源码、配置和测试        | 以目标上游实现为基线；Ki-Buddy 自有改动只接受通用改进或薄接缝 |

产品拥有文件包括 Ki-Buddy 产品配置、明确命名的产品 contract/runtime adapter、产品页面和对应测试。新增产品文件使用 `ki-buddy` 或 `kiBuddy` 语义，使其可以通过搜索识别。

现有 ADR 可以批准领域模块的结构例外。例如 [ADR 0003](../adr/0003-project-agents-identity-into-core-user.md) 将身份相关主进程代码放在 `process/ki-buddy/`。此类例外只覆盖 ADR 声明的领域；新的产品领域仍先按 `architecture` skill 选址，需要新的结构例外时另建 ADR。

### 2.2 变更分类

每个修改文件或 hunk 必须归入下列变更类型。一个文件可以包含多种类型，但每种类型都要对应可定位的 hunk 或来源证据：

| 变更类型 | 允许位置           | 判定标准                                                                      |
| -------- | ------------------ | ----------------------------------------------------------------------------- |
| 产品实现 | 产品拥有文件       | 承担 Ki-Buddy 业务、状态、协议或 UI                                           |
| 集成接缝 | 上游拥有文件       | 只检测、选择、注册或转发到产品模块                                            |
| 通用改进 | 上游拥有文件       | 删除 Ki-Buddy 后仍有独立价值和正确语义                                        |
| 上游同步 | 上游拥有文件       | 可追溯到已选择 AionUi commit 的上游原始变化，不包含产品适配                   |
| 支撑材料 | 产品或上游拥有文件 | 测试、ADR、spec、i18n 资源或生成文件；指向其支持的其他变更，不含 runtime 逻辑 |

无法归类的修改不得提交。同一 hunk 不能用多个类型掩盖职责。产品实现进入上游拥有文件时，应移到产品模块；名为通用改进但只有 Ki-Buddy 使用时，应改为显式产品模块或接缝；产品适配不能藏在上游同步中；runtime 逻辑不能归为支撑材料。

### 2.3 非 runtime 例外

纯 CI/CD、打包与发布链路不参与第 1–4 节的产品所有权、变更分类和接缝约束，也不参与第 6 节的产品接缝审查。例外包括：

- CI workflow 与发布 workflow；
- 打包、分发和 updater 配置；
- release script、版本映射、checksum、provenance 与发布来源验证；
- 只验证上述行为的测试、fixture 和生成文件。

这些变更仍遵循 `AGENTS.md`、`CONTRIBUTING.md`、对应 release skill 和发布文档。Release 侧可以按自己的执行环境解析产品清单，不要求与 runtime 共用解析入口；它必须按发布 contract 独立验证输入。

例外按 hunk 判定。一个文件同时包含 runtime 与发布行为时，只有纯发布 hunk 适用例外；应用启动后会执行或直接影响 runtime 语义的代码与配置继续遵循本规范。

## 3. 产品接入边界

### 3.1 产品配置

- 产品默认值和 runtime identity 由 Ki-Buddy 产品配置管理。
- AionUi 公共配置和通用 fallback 保持原有语义。
- 产品配置由单一解析入口读取，消费端不重复产品常量。
- 产品配置解析失败时返回明确错误或定义过的产品默认行为，不隐式采用 AionUi 产品身份。

### 3.2 Runtime capability

- 主进程或 preload 显式暴露产品 capability；应用名称、品牌文本和通用 Electron 环境不作为能力判断。
- capability contract 保持窄、可序列化、可版本化，只暴露 renderer 所需的产品操作。
- 同类 capability 只有一个检测和访问入口；共用入口只选择产品 adapter，不解析产品协议或维护产品状态。
- capability 缺失时，AionUi 原路径保持可达，并且产品模块不初始化副作用。

### 3.3 UI

- 产品页面和页面私有组件由 Ki-Buddy 拥有；导航、Router、Settings 等上游入口只保留 lazy mount 或产品入口。
- 复用 AionUi 公开组件、design token 和交互模式；差异通过组合、参数、包装组件或产品私有子组件表达。
- 参考生产包时提取布局与交互经验，再用仓库公开组件实现。私有 API、私有服务、品牌素材和无法确认授权的实现不进入 Ki-Buddy。
- 公共 i18n 模块是产品接缝规则的明确例外：它可以通过显式 Ki-Buddy runtime capability 选择产品默认语言，区分并持久化产品语言与用户选择语言。Capability 缺失时必须保持 AionUi 原有初始化和持久化语义。
- i18n 例外只覆盖语言初始化与持久化，不覆盖认证状态、页面流程或产品文案。所有用户可见文本仍遵循 `i18n` skill；产品文案不得写入 AionUi 公共 locale 的通用语义。

### 3.4 数据与外部系统

- 产品 storage key、系统凭据 namespace、数据目录和 cache namespace 与 AionUi 及其他环境隔离。
- 外部平台协议集中在产品 client/adapter 中；UI、bridge 和上游 service 不拼接 endpoint 或解析供应商信封。
- 安全例外限制到明确目标与单次请求，不通过全局开关改变 AionUi 或其他网络流量。
- 产品迁移与生命周期规则由对应产品模块和 ADR 拥有，不向 AionUi 通用 migration 注入产品假设。

## 4. 接缝标准

新增或修改接缝时，必须同时满足：

1. **薄**：只检测、选择、注册或转发。
2. **显式**：通过产品或 capability 名称可以搜索发现。
3. **集中**：同类判断只有一个入口和一个选择点。
4. **可移除**：移除接缝后，AionUi 原路径仍完整。
5. **可验证**：runtime 接缝覆盖 capability 存在与缺失；配置接缝分别验证 Ki-Buddy 产品配置与 AionUi 公共配置语义。
6. **可替换**：上游出现正式扩展点后，产品逻辑无需重写即可迁移。
7. **低扰动**：不混入无关格式化、重命名、移动或代码整理。

以下情况必须在提交前调整：

- 多个上游组件重复判断 Ki-Buddy runtime；
- 通用 context 保存只有 Ki-Buddy 使用的业务状态；
- 复制上游页面、context 或 service 后长期独立修改；
- 公共配置写入 Ki-Buddy 默认值；
- 名称通用的抽象实际只有 Ki-Buddy 语义；
- 接缝修改同时重排无关上游代码。

## 5. 开发与审查

### 5.1 开始前

1. 固定目标 AionUi 基线与 merge-base。
2. 阅读 issue/spec、相关 ADR、产品模块和目标上游实现。
3. 搜索上游已有扩展点，并按第 1 节顺序选择方案。
4. 建立变更分类表：

| 文件或 hunk          | 所有权      | 变更类型                                         | 职责、通用价值或支撑对象 | 上游原行为   | 验证证据 |
| -------------------- | ----------- | ------------------------------------------------ | ------------------------ | ------------ | -------- |
| `<path>[:line/hunk]` | 产品 / 上游 | 产品实现 / 接缝 / 通用改进 / 上游同步 / 支撑材料 | `<reason>`               | `<behavior>` | `<test>` |

产品实现、上游同步与支撑材料不要求填写“上游原行为”；上游同步和测试文件不要求填写“验证证据”。上游同步行填写目标 AionUi commit；其余列必须有可核验内容。新增文件或扩大范围时同步更新表格。

完成标准：预计修改的每个文件均已覆盖，混合职责文件按 hunk 分列；每个包含 runtime 或配置行为的上游拥有文件都有独立修改理由和测试位置。

### 5.2 实现时

- 从产品 API 向上游入口工作：先定义产品能力，再添加调用它的接缝。
- 新增上游修改面时，重新检查能否通过既有接缝、依赖注入或产品组合完成。
- 上游通用改进与产品功能可以独立合并时，分成独立 PR。
- 无法通过薄接缝实现的深层上游修改先建立 ADR，记录修改范围、同步成本和退出条件。

完成标准：共用改动无需理解产品业务即可审查；变更分类表覆盖实际 diff。

### 5.3 验证

按 `testing`、`i18n` 和 `AGENTS.md` 执行适用检查；自动化测试不依赖真实账号、固定内网地址或互联网连通性。runtime 接缝验证 capability 存在和缺失两个分支；配置接缝验证 Ki-Buddy 产品配置和 AionUi 公共配置语义。

完成标准：适用的仓库检查和接缝双分支证据通过。

## 6. Standards 审查契约

`code-review` 的 Standards 轴审查包含 Ki-Buddy 产品文件、接缝或 AionUi 基线同步的 diff 时，必须把本规范列为 standards source，并对完整固定范围执行以下检查。

审查开始时先按第 2.3 节标记纯 CI/CD、打包和发布 hunk。它们计入完整 fixed-point diff 的覆盖记录，但不接受产品所有权、变更分类、接缝或 smell 判断；审查者只对其余 hunk 执行本节检查。通用工程或 release 专项审查不受该例外影响。

### 6.1 重建变更清单

审查者不能依赖实现阶段的对话或计划。根据 `git diff <fixed-point>...HEAD` 自行重建第 5.1 节的变更分类表：

- 每个 runtime 和配置文件单独列出；
- 测试、文档、i18n 和生成文件可以按同一支撑对象分组；
- 第 2.3 节的纯 CI/CD、打包和发布 hunk 可以按来源分组标记为“非 runtime 例外”，不要求归入第 2.2 节的变更类型；
- 与目标 AionUi commit 一致的上游同步文件可以按来源 commit 分组；冲突处理或产品适配涉及的文件必须单独列出；
- 除第 2.3 节例外外，每个上游拥有文件或 hunk 必须判定为接缝、通用改进、上游同步、支撑材料或违规的产品实现；
- commit list 和实际 diff 都纳入审查，不能只检查最后一次提交。

完成标准：diff 中每个文件均被覆盖；非 runtime 例外已按 hunk 标记；其余混合职责文件按 hunk 分类；没有用“支撑材料”或“非 runtime 例外”掩盖 runtime 逻辑。

### 6.2 硬性违规

以下问题作为 documented-standard breach 报告：

- 产品业务、状态、协议或 UI 进入上游拥有文件，而不是产品模块；
- 接缝承担第 2.2 节允许范围之外的产品逻辑；
- 产品识别绕过显式 capability，或同类 capability 存在多个访问入口；
- runtime capability 缺失时 AionUi 原路径不可达、产生产品副作用，或没有保护测试；
- 配置接缝无法分别证明 Ki-Buddy 产品配置与 AionUi 公共配置语义；
- Ki-Buddy 配置、identity、数据 namespace 或默认值改写 AionUi 公共语义；
- 外部平台协议泄露到 UI、上游 service 或通用 bridge，或安全例外影响非目标流量；
- 产品适配被归为上游同步，或上游同步内容无法追溯到选定 AionUi commit；
- 深层修改上游拥有文件，却没有满足第 8 节的 ADR；
- 自动化测试依赖真实账号、固定内网地址或互联网连通性。

### 6.3 设计判断

以下问题作为 judgement call 报告，并说明同步成本：

- 接缝不再薄、集中、可移除或可替换；
- 重复上游页面、context、service 或产品条件；
- 通用抽象实际只表达 Ki-Buddy 语义；
- 接缝 diff 包含无关重排、重命名、移动或格式变化；
- 目标上游已经提供正式能力，本地替代实现仍被保留；
- 单个产品变化需要修改过多上游拥有文件，呈现 Shotgun Surgery。

### 6.4 报告要求

每项发现引用代码文件/hunk 和本规范章节，区分“硬性违规”与“设计判断”。只有在每个变更文件都完成分类或按第 2.3 节标记例外、每个接缝都检查第 4 节、runtime 接缝的无 capability 路径及配置接缝的 AionUi 公共配置语义都有证据后，才能报告 Standards 无发现。

## 7. 跟随上游更新

本节从目标 AionUi commit 已确定开始，只规定源码差异的处理方式。

### 7.1 同步前

- 固定当前与目标 AionUi commit。
- 从当前产品 diff 生成变更分类表，列出全部产品拥有文件、接缝、通用改进、上游同步和支撑材料。
- 阅读目标版本中与这些文件和公开接口相关的变化，标出上游已经提供的替代能力。

### 7.2 处理差异

- **上游同步**：采用目标 commit 的上游内容；冲突处理或产品适配单独归类。
- **产品拥有文件**：保留产品语义，适配目标上游公开 contract。
- **接缝**：以目标上游文件为基线重新建立最薄装配点，不机械保留旧冲突块。
- **通用改进**：确认目标上游是否已包含；已包含则采用上游版本，仍缺失才保留。
- **上游已覆盖的产品实现**：验证语义等价后迁移，并删除本地重复代码。

完成标准：目标上游新增行为未被旧本地代码覆盖；产品通过目标基线的公开接口运行；新增或扩大的接缝均有明确理由。

### 7.3 同步后

- 对比同步前后的变更分类表，解释新增、扩大、缩小和删除的接缝。
- 执行缺失/存在 capability 回归和完整测试。
- 检查产品配置、协议、数据 namespace 和 runtime capability 仍属于 Ki-Buddy。
- 新的长期架构决定写入 ADR；一次性的冲突处理不写入本规范。

## 8. 例外与退出条件

深层修改上游拥有文件的 ADR 必须记录：

- 现有扩展点为何不足；
- 修改的上游文件与产品职责；
- AionUi 原行为的保护测试；
- 每次上游同步的复查项；
- 上游出现什么能力后删除本地实现。

已有例外只覆盖原 ADR 声明的领域，不能作为后续深层修改的通用依据。
